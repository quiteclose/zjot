# zjot

A Djot parser written in Zig. Provides both a library for programmatic use and a CLI for rendering Djot documents.

## References

This project applies lessons learned from a draft Zig implementation to produce a clean, modular parser with robust source position tracking and a proper public API.

The reference implementations used during development are:

- **djot.js** -- John MacFarlane's canonical JavaScript implementation (2-phase event stream to AST)
- **jotdown** -- Rust implementation (2-phase block events to inline events)

zjot parses in two block-streaming passes (see Architecture): a recursive descent over lines yields one block's `Node` tree at a time, with no event stream and no whole-document tree.

## Architecture

```
src/
  root.zig           Library root: public API (render, toHtml, toAst, toAstOpts)
  main.zig           CLI binary (--ast, --sourcepos, file/stdin)
  node.zig           Node, Tag, Attr, SourcePos, CellAlign
  Parser.zig         Block parsing, container windows, list helpers
  document.zig       Document-level state: Survey (ids, auto refs), Resolver, Sections
  inline.zig         Inline parsing (parseInlineContent + all handlers)
  attributes.zig     AttrParser state machine, BlockAttrs
  html.zig           HTML renderer
  ast.zig            AST renderer (indented text format matching djot.js)
  LineMap.zig         Source position mapping for inline content
  test_runner.zig    Test harness for .test files
test/
  *.test             Vendored djot.js test files (26 files; 25 run, 261 test cases)
  zjot.test          zjot's own cases (398), expectations generated by djot.js 0.3.2
  cli/               CLI golden fixtures: NAME.dj with NAME.html, NAME.ast, NAME.sourcepos.ast
```

### Module responsibilities

- **root.zig** -- Public API. `render(a, input, writer, opts)` streams the document block by block: pass one surveys with `nextBlock` and a block arena reset after every block; pass two resolves, sections and writes each block the same way. Only the line index, `Definitions` and `Survey` live for the document. `toHtml`, `toAst`, `toAstOpts` are `render` into an owned slice.
- **node.zig** -- AST types. `Tag` enum (40 tags, each produced by the parser), `Node` struct with children, text, attributes (class is an attribute like any other), list start and style, source positions. `Attr`, `SourcePos`, `CellAlign`, `ListStyle`.
- **Parser.zig** -- Block-level parsing, block-local: `nextBlock` yields one block at a time and never generates ids or resolves references. Every parser is a window onto the document's `LineIndex` (a run of lines, each with the bytes its containers stripped); a container's content is parsed by a child window (`Window`, `child`) that keeps a pointer to the parser it is inside, so positions come straight from the index (`makePos`) and a block ending at the window's end asks the enclosing parser where its container stopped (`containerEnd`, `stopBefore`, `endAtBlank`, `afterNewline`). Owns `Definitions` (ref defs and footnote defs, allocated for the document's lifetime) shared by pointer with child parsers. Contains `parseBlocks`, `try*` block functions (one `tryList` for bullet and ordered lists), the item helpers (`collectItemContent`, `parseItemContent`), and LineMap-based inline position tracking.
- **document.zig** -- Document-level state, split by lifetime. `Survey` visits every block once and assigns heading ids (djot.js rule: document order, each generated id avoiding every id seen so far) and auto references. `Resolver` resolves one block at a time against the definitions and the survey (ids by ordinal, links by label), and a footnote definition on request. `Sections` turns headings into open/close events without allocating. `root.render` drives the three and, after the document, the footnotes: the endnotes in first-use order in HTML, every definition in the AST.
- **inline.zig** -- Inline parsing. `parseInlineContent` runs a `Scanner` (opener stack, items, `resolveItems`) over one block's joined text; every node is made with the span of source it came from and, when the caller passes a `LineMap`, its document position. Handlers for emphasis, links, smart quotes, super/subscript, insert/delete/mark, math, symbols, raw inline, autolinks.
- **attributes.zig** -- Attribute parsing. `AttrParser` state machine for `{#id .class key=value}` syntax. `BlockAttrs` struct. Block and inline attribute parsing entry points.
- **html.zig** -- HTML rendering. `Renderer` walks one block's `Node` tree; `Footnotes` numbers footnotes by first reference across blocks, as djot.js's renderer does, and `renderEndnote` writes each endnote from the definition's resolved blocks.
- **ast.zig** -- AST rendering. Walks the `Node` tree and produces indented text format matching djot.js test expectations; every footnote definition follows the document as a `footnote` block (see the `zjot.test` header).
- **LineMap.zig** -- Maps byte offsets in joined inline text back to source positions: one segment per content line, built by `Parser.buildInlineLineMap`; the newline joining two lines resolves to col 0 of the line after it.
- **test_runner.zig** -- Parses `.test` files (backtick-fenced input/output pairs) and runs them against the parser.

### Key design decisions

1. **Definitions by pointer, with their own allocator** -- Child parsers (for list items, blockquotes, etc.) receive a `*Definitions` pointer instead of copying hash maps in and out, so a definition inside a container is visible to the parent. Everything stored there is duped into `Definitions.a`, so definitions outlive the block that produced them whatever allocator the blocks use.

2. **The inline parser records spans; the block parser supplies the map** -- When content lines are joined for inline parsing, `Parser.buildInlineLineMap` creates a `LineMap` from the lines' original positions and hands it to `parseInlineContent`. The `Scanner` makes every node through `emit` (a span of the joined text, both ends inclusive, as djot.js reports inline positions) or `text` (a slice of it), resolving the span through the map as the node is made, so no node is positioned after the fact and none is missed. Text contiguous in the source is one `str`, as djot.js; an open bracket stays its own item because its opener's index points at it.

3. **One list parser** -- `tryList` parses bullet and ordered lists over a `Marker` (`parseBulletMarker`, `parseOrderedMarker`); only what the next marker must match differs (the bullet character and task-ness, or a shared number style narrowed by `OrderedStyles`). `collectItemContent` handles para line collection (with sourcepos tracking arrays), block continuation after blanks (lazy continuation stops at `isBlockStartAt`, the same predicate footnote definitions use), and trailing blank trimming. `parseItemContent` parses the item's paragraph window and its block window as children and returns the merged blocks. `updateListTightness` centralizes tightness detection.

4. **Proper error handling** -- Public API uses Zig error unions (`!` return types). The parser degrades gracefully on malformed input but propagates allocation failures.

5. **Render-only surface** -- The public API is `render` and the `to*` wrappers. `Node` is the currency between the parser, `document.zig` and the renderers, not an exported tree; a tree API, if one is ever needed, would be built on `Survey`, `Resolver` and `Sections` the way `render` is.

## Test suite

Test files are vendored from `djot.js/test/` into `test/`. Each `.test` file contains backtick-fenced test cases:

```
` ` ` [options]
input
.
expected output
` ` `
```

Options: `a` = AST mode (compare against AST output instead of HTML), `p` = sourcepos (include source positions in AST).

Run tests: `zig build test`

Run them on WASI (needs wasmtime): `zig build test -Dtarget=wasm32-wasi -fwasmtime`

### zjot's own cases

`test/zjot.test` holds cases the vendored suite does not: behaviour zjot once got wrong, in
the same format and run by the same harness. Every expectation is generated, never written
by hand:

```
npx -y @djot/djot@0.3.2 input.dj
```

A case goes in only when zjot and djot.js agree on it. Where zjot deliberately differs from
djot.js, the file's header records the difference instead of a case pinning it. The
version is pinned in the header; re-checking against a newer djot.js is a deliberate act
(CI has no npm).

`test/tools/` holds the two local tools behind the generated expectations (both need
`npx`, so CI never runs them):

- `djot2ast.py` renders djot.js's `-t ast -p` JSON in the `.test` files' AST text form; every
  `ap` case in `zjot.test` was made with it (`python3 test/tools/djot2ast.py -p < input.dj`).
- `diff-djot.sh` runs zjot and djot.js over every `test/cli/*.dj` and `test/tools/corpus/*.dj`
  (a nested-container corpus) in HTML and `--ast --sourcepos`, prints a unified diff per
  divergence and exits 1 if there was one, so a divergence is one command away. The
  deliberate differences in the `zjot.test` header are the only expected output. Run it
  after `zig build`; pass file paths to check a subset.

### CLI goldens

`zig build cli-test` runs the binary against `test/cli/`: one fixture per block family
(`hi`, `headings`, `inlines`, `lists`, `code`, `blockquote`, `table`, `footnotes`), each in
HTML, `--ast` and `--ast --sourcepos` mode, plus the stdin, `-`, option and error cases
written inline in `build.zig`. The goldens test the CLI path (argv to bytes on stdout, exit
code), not the parser; parser behaviour belongs in the `.test` suite.

To add a fixture: write `test/cli/NAME.dj`, generate the three expected files with the
binary and read them, then add `NAME` to `fixtures` in `build.zig` (in that order: the
build script reads every registered golden at configure time and stops on a missing one):

```
zig build
zig-out/bin/zjot test/cli/NAME.dj > test/cli/NAME.html
zig-out/bin/zjot --ast test/cli/NAME.dj > test/cli/NAME.ast
zig-out/bin/zjot --ast --sourcepos test/cli/NAME.dj > test/cli/NAME.sourcepos.ast
```

Regenerate the same way after an intended output change, and review the diff: the
expected files pin zjot's own output, so a regeneration accepts whatever the binary does.

## Implementation status

All 261 djot.js test cases pass, plus the 398 cases in `test/zjot.test`. The parser is feature-complete for the Djot specification as tested by the canonical test suite. Source position tracking is implemented and verified.
