# zjot

A Djot parser written in Zig. Provides both a library for programmatic use and a CLI for rendering Djot documents.

## References

This project applies lessons learned from a draft Zig implementation to produce a clean, modular parser with robust source position tracking and a proper public API.

The reference implementations used during development are:

- **djot.js** -- John MacFarlane's canonical JavaScript implementation (2-phase event stream to AST)
- **jotdown** -- Rust implementation (2-phase block events to inline events)

zjot parses in one block-streaming pass (see Architecture): a container stack over the input's lines, the shape of djot.js's block parser, yields one block's `Node` tree at a time, with no event stream and no whole-document tree; a block is written as soon as nothing in it can still change.

## Architecture

```
src/
  root.zig           Library root: public API (render, renderReader, toHtml, toAst, toAstOpts)
  main.zig           CLI binary (--ast, --sourcepos, file/stdin, streamed)
  node.zig           Node (common fields + a per-tag Payload), Tag, Attr, SourcePos, CellAlign
  Parser.zig         Block parsing: the container stack over lines, one block at a time
  leaf.zig           The leaf parsers' bodies: block starts, markers, fences, table rows
  document.zig       Document-level state: Definitions, Ids (heading ids, implicit references), Resolver, Sections
  inline.zig         Inline parsing (parseInlineContent + all handlers)
  attributes.zig     AttrParser state machine, BlockAttrs
  html.zig           HTML renderer
  ast.zig            AST renderer (indented text format matching djot.js)
  LineMap.zig         Source position mapping for inline content
  Lines.zig          The line source: lines with positions from a slice or a std.Io.Reader
  test_runner.zig    Test harness for .test files
test/
  *.test             Vendored djot.js test files (26 files; 25 run, 261 test cases)
  zjot.test          zjot's own cases (683), expectations generated by djot.js 0.3.2
  grid.test          Generated whole by test/tools/gen-grid.py: every block family × wrapper × mode, and the waiting shapes
  cli/               CLI golden fixtures: NAME.dj with NAME.html, NAME.ast, NAME.sourcepos.ast
```

### Module responsibilities

- **root.zig** -- Public API. `render(a, input, writer, opts)` and `renderReader(a, reader, writer, opts)` (over `Lines.fromSlice` and `Lines.fromReader`) read the input once and stream the document block by block: each block from `nextBlock` comes in an arena of its own (the parser's, swapped for a fresh one the moment a top-level block closes), gets its heading ids from `Ids`, and goes through `Output`, which writes it at once when nothing in it can still change and otherwise queues it (a block holding a reference-style link waits for the input's end, since a later definition replaces an earlier one; under `--ast --sourcepos` a section open waits for the heading that closes it, which gives its end). The queue drains from the front as entries become ready; an entry that waits for nothing but stands behind one that does is rendered as it arrives and keeps only its text (HTML footnotes are numbered in document order first, then through every definition's content in definition order before the endnotes are written, as djot.js), so a wait costs the waiting block's tree and the output behind it, and the output after the first reference-style link is buffered to the end. A rendered block's arena goes back to the parser (`recycle`) for the next block; a held section open keeps its own copies of the id and attributes it takes from its heading (`HeldSection`), so the heading's arena goes back like any other. Only `Definitions`, `Ids` and the waiting blocks live for the document. `toHtml`, `toAst`, `toAstOpts` are `render` into an owned slice.
- **node.zig** -- AST types. `Tag` enum (every tag produced by the parser); `Node` carries what every node has (attributes, with class an attribute like any other; the id the document gave it; source positions) and `data: Payload`, a `union(Tag)` of what only its kind carries: a container's children, a leaf's text, a heading's level, a list's style and tightness, a cell's alignment, a link's destination and reference. `children()` and `text()` read across kinds for the walks that need them (ids, alt text, string content). `Attr`, `SourcePos`, `CellAlign`, `ListStyle`, `Link`.
- **Parser.zig** -- Block-level parsing, block-local: a container stack, the shape of djot.js's `block.js`, in one pass over `Lines`. Each line is run against the open containers from the outermost in (`continues`), then against the block starts while the innermost matched container holds blocks (`tryOpen`, djot.js's order); the rest is lazy text for an open paragraph or heading, a blank line, or the innermost container's text. A container closes when a line neither continues it nor is lazy text for it, its node ending where the parser stands (djot.js's event position: a list item one before it, a fenced block on its fence); `nextBlock` returns each top-level block as it closes and never generates ids or resolves references. Block attributes wait in the container they were written in; list tightness follows `parse.js`'s rule on the same events; a footnote's content is allocated for the document while it is open and recorded into `document.Definitions` when it closes, as reference definitions are; a caption joins the table before it, so a closed top-level table is held until a block follows it (djot.js attaches captions across blank lines and definitions). The parser's own state (the stack, the open leaf's lines, spare children lists) lives in reusable buffers; nodes come from the arena of the block being built, which `nextBlock` hands over with the block (`Parser.Block`) and takes back through `recycle`. A closed top-level block is held until a block follows it or the input ends, so a caption can still join it.
- **leaf.zig** -- What one line, or one leaf block's lines, say on their own, with no document or container state: the block starts (`headingLevel`, `isCodeFence`, `startsBlockQuote`, `isFencedDivStart`, `definitionLabel`, `isTableRow`, the list markers and `OrderedStyles`), fence closers, table rows and cells (`rowCells`, `parseSepAligns`), captions and the whitespace helpers. The block parser decides where each applies.
- **document.zig** -- Document-level state, split by lifetime. `Definitions` holds the reference and footnote definitions for the document, whatever allocator the blocks use. `Ids` writes heading ids into each block as it arrives (the parser built the tree for that block alone), and into each footnote definition where it stands among the headings (the parser counts headings and explicit ids as it meets them, and logs each definition as it opens and each id it reads off a node where it stands; a table's rows claim before its caption, which is written after them; a definition item's term loses its node with its id, which is logged where it stood, as are an inline attribute's attached to nothing or overridden and a dropped caption's, and a replaced caption's are put into the log where they were counted; nesting past `max_nesting` (1000 levels, a footnote definition a level where it stands, its blocks under it) is `error.TooDeep` from the parser alone, before any walker recurses: no node is made past it (each container knows its node's depth, and the rows, cells, captions and terms made without one are checked as they are made), and the first walk over a leaf's inlines counts them from the leaf's depth (`boundLeaf`, which also keys a link's label once what is below it is bounded); `Ids` walks each definition from where it stands, so no walk recurses deeper; djot.js rule: document order, each generated id avoiding every id seen so far), lets the first heading with a text claim it as an implicit reference, and reports whether the block holds a link by reference, which must wait for the definitions. `Resolver` resolves a block's reference links against the definitions and the implicit references once they are final, and a footnote definition on request. `Sections` turns headings into open/close events without allocating, moving a heading's id and attributes onto the section it opens in the events (the heading node the parser made keeps them, so a writer built on `nextBlock` sees them where they were written; djot.js's own AST has them on the section only); the consumer fills in a section's end when it closes (where the heading that closes it ends, as djot.js). `root.render` drives the three and, after the document, the footnotes: the endnotes in first-use order in HTML, every definition in the AST.
- **inline.zig** -- Inline parsing. `parseInlineContent` runs a `Scanner` (opener stack, items, `resolveItems`) over one block's joined text; every node is made with the span of source it came from and, when the caller passes a `LineMap`, its document position. Handlers for emphasis, links, smart quotes, super/subscript, insert/delete/mark, math, symbols, raw inline, autolinks. A link closes on the forward pass, as djot.js: `](` or `][` marks its bracket's opener, and the `)` or `]` the pass comes to closes it, the destination or label read off the source.
- **attributes.zig** -- Attribute parsing. `AttrParser` state machine for `{#id .class key=value}` syntax. `BlockAttrs` struct. Block and inline attribute parsing entry points.
- **html.zig** -- HTML rendering. `Renderer` walks one block's `Node` tree; `Footnotes` numbers footnotes by first reference across blocks, as djot.js's renderer does, and `renderEndnote` writes each endnote from the definition's resolved blocks.
- **ast.zig** -- AST rendering. Walks the `Node` tree and produces indented text format matching djot.js test expectations; every footnote definition follows the document as a `footnote` block (see the `zjot.test` header).
- **Lines.zig** -- The line source: `Lines.next` yields one line at a time (newline and carriage return stripped) with its position, from a resident slice (zero-copy, lines stable for the document) or from a `std.Io.Reader` (a line is valid until the next call; one longer than the reader's buffer spills into a growing buffer); `end` is where the input ended, as djot.js reports it, and each line carries its `eol` (col 0 of the next line); the counts are 64-bit (`error.InputTooLarge` at 2^64 bytes or lines, the one size limit) and a position saturates past 4 GiB. The source the parser reads from.
- **LineMap.zig** -- Maps byte offsets in joined inline text back to source positions: one segment per content line, built by `Parser.leafLineMap`; the newline joining two lines resolves to col 0 of the line after it.
- **test_runner.zig** -- Parses `.test` files (backtick-fenced input/output pairs) and runs them against the parser.

### Key design decisions

1. **Definitions for the document, blocks for themselves** -- A footnote or reference definition is recorded into `Definitions` the moment its container closes, wherever it sits, and everything kept there (a footnote's content included, which the parser allocates from `Definitions.a` while the footnote is open) outlives the block it came in. Every other node lives in its block's arena, which the parser hands over with the block and takes back once the block is written, so a document's memory is its definitions, its ids and whatever waits to be written.

2. **The inline parser records spans; the block parser supplies the map** -- When content lines are joined for inline parsing, `Parser.leafLineMap` creates a `LineMap` from the lines' original positions and hands it to `parseInlineContent`. The `Scanner` makes every node through `emit` (a span of the joined text, both ends inclusive, as djot.js reports inline positions) or `text` (a slice of it), resolving the span through the map as the node is made, so no node is positioned after the fact and none is missed. Text contiguous in the source is one `str`, as djot.js, but for the text of an unclosed marked opener (`{_`), which starts a `str` of its own as djot.js's open marker breaks its run; an open bracket stays its own item because its opener's index points at it.

3. **Lists on the stack** -- A `list` container holds items and a `ListStyle` (the bullet character, task, definition, or an ordered list's possible styles and delimiter, read off the marker by `leaf.parseBulletMarker`/`parseOrderedMarker`); a marker of its style continues it whatever its indent, narrowing an ordered list's styles (`OrderedStyles.accept`), and a new item closes whatever is open above the list, as djot.js's `addContainer`. Tightness is `parse.js`'s rule run on the parser's own events: a blank line marks the innermost list (the tip, or the list the tip's item is in); the next container opened or closed that is not a list start or a list or item end makes it loose, and anything but an item boundary clears the mark. So a blank line belongs to the innermost open list, and a sublist before or after it absorbs it.

4. **Proper error handling** -- Public API uses Zig error unions (`!` return types). The parser degrades gracefully on malformed input but propagates allocation failures.

5. **Render-only surface** -- The public API is `render` and the `to*` wrappers. `Node` is the currency between the parser, `document.zig` and the renderers, not an exported tree; a tree API, if one is ever needed, would be built on `Ids`, `Resolver` and `Sections` the way `render` is.

## Test suite

Test files are vendored from `djot.js/test/` into `test/`. Each `.test` file contains backtick-fenced test cases:

```
` ` ` [options]
input
.
expected output
` ` `
```

Options: `a` = AST mode (compare against AST output instead of HTML), `p` = sourcepos (include source positions in AST).

Run tests: `zig build test`

Run them on WASI (needs wasmtime): `zig build test -Dtarget=wasm32-wasi -fwasmtime`

### zjot's own cases

`test/zjot.test` holds cases the vendored suite does not: behaviour zjot once got wrong, in
the same format and run by the same harness. Every expectation is generated, never written
by hand:

```
npx -y @djot/djot@0.3.2 input.dj
```

A case goes in only when zjot and djot.js agree on it. Where zjot deliberately differs from
djot.js, the file's header records the difference instead of a case pinning it. The
version is pinned in the header; re-checking against a newer djot.js is a deliberate act
(CI has no npm).

`test/grid.test` is generated whole by `test/tools/gen-grid.py` (never edited by hand): every
block family bare, under a block attribute, in a block quote and in a list item, in HTML and
with positions, plus the shapes that make a block wait for a later one (a reference defined
after use, an implicit reference before and after its heading, two headings with one text,
footnotes defined before and after use, a definition redefined). The generator compares
zjot's output as it goes and reports every divergence; headings in it carry explicit ids
since zjot prints generated ones and djot.js does not.

`test/tools/` holds the local tools behind the generated expectations (all need `npx`, so
CI never runs them):

- `djot2ast.py` renders djot.js's `-t ast -p` JSON in the `.test` files' AST text form; every
  `ap` case in `zjot.test` was made with it (`python3 test/tools/djot2ast.py -p < input.dj`).
- `gen-grid.py` writes `test/grid.test` (above), after `zig build` to compare.
- `diff-djot.sh` runs zjot and djot.js over every `test/cli/*.dj` and `test/tools/corpus/*.dj`
  (a nested-container corpus) in HTML and `--ast --sourcepos`, prints a unified diff per
  divergence and exits 1 if there was one, so a divergence is one command away. The
  deliberate differences in the `zjot.test` header are the only expected output. Run it
  after `zig build`; pass file paths to check a subset.

### CLI goldens

`zig build cli-test` runs the binary against `test/cli/`: one fixture per block family
(`hi`, `headings`, `inlines`, `lists`, `code`, `blockquote`, `table`, `footnotes`; and
`nofinal`, an unclosed code block whose last line has no newline, which the `.test` format
cannot carry), each in
HTML, `--ast` and `--ast --sourcepos` mode, plus the stdin, `-`, option and error cases
written inline in `build.zig`. The goldens test the CLI path (argv to bytes on stdout, exit
code), not the parser; parser behaviour belongs in the `.test` suite.

To add a fixture: write `test/cli/NAME.dj`, generate the three expected files with the
binary and read them, then add `NAME` to `fixtures` in `build.zig` (in that order: the
build script reads every registered golden at configure time and stops on a missing one):

```
zig build
zig-out/bin/zjot test/cli/NAME.dj > test/cli/NAME.html
zig-out/bin/zjot --ast test/cli/NAME.dj > test/cli/NAME.ast
zig-out/bin/zjot --ast --sourcepos test/cli/NAME.dj > test/cli/NAME.sourcepos.ast
```

Regenerate the same way after an intended output change, and review the diff: the
expected files pin zjot's own output, so a regeneration accepts whatever the binary does.

## Implementation status

All 261 djot.js test cases pass, plus the 683 cases in `test/zjot.test` and the 115 generated in `test/grid.test`. The parser is feature-complete for the Djot specification as tested by the canonical test suite. Source position tracking is implemented and verified.
